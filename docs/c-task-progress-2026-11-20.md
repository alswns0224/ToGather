# Task 전체·담당자별 진행 현황과 서버 필터

2026-11-20. 설계 대조의 우선순위 7번(G02)을 보완했다. SD-09-07(본문 69쪽), TaskProgress(C-DTO-17, 146쪽)에 해당한다. 원본 저장소 `feature/c-fix-task-rules`에서 앞선 변경 위에 작업했다.

## 바뀐 동작

- 목록의 진행 중·완료·마감 주의 건수를 현재 페이지의 최대 20건으로 계산하던 문제를 고쳤다. 같은 조회 조건에 맞는 모든 Task를 집계한다.
- 전체 평균 진행률, 정상·주의·위험 건수와 담당자별 작업 수·완료 수·평균 진행률·위험 건수를 제공한다. 작업이 없는 현재 팀원과 담당자 미지정도 0으로 표시한다. 이전 팀원에게 남아 있는 작업도 집계에서 빠뜨리지 않는다.
- 평균 진행률은 `floor(개별 Task 진행률 합 / Task 수)`다. 개별 진행률은 기존처럼 제출된 산출물 비율을 내림하며, 산출물이 없으면 완료 100%, 진행 중 0%다. 빈 목록의 평균은 0%다. 산출물 개수가 많은 Task에 가중치를 추가하지 않는다.
- 정상·주의·위험은 기존 Task 상세와 같은 도메인 규칙을 재사용한다. 완료 Task와 마감 미정 Task는 정상이며, 날짜는 한국 시간 기준이다. 응답에 `asOfDate`를 표시한다.
- 내 담당, 특정 담당자, 미지정, 진행 중/완료, 제목 검색과 마감일 조건을 서버에서 페이지를 나누기 전에 적용한다. 목록·집계에 동일한 조건을 사용한다.
- 제목 검색은 대소문자를 구분하지 않는 일반 부분 문자열 검색이다. `%`, `_`, 따옴표를 SQL 조건이나 와일드카드로 해석하지 않는다.
- 최근 생성순은 생성 시각과 ID 내림차순, 마감일순은 미정 마감을 마지막에 두고 같은 날짜에는 생성 시각·ID를 사용한다.
- 필터를 바꾸면 첫 페이지로 이동한다. 조회 중 늦게 도착한 이전 응답을 무시하며, 생성·수정·삭제 후에는 목록과 집계를 다시 조회한다. 마지막 페이지가 비면 마지막 유효 페이지로 이동한다.
- 집계와 목록 실패를 따로 표시하고 재시도할 수 있다. 집계 실패를 0건으로 표시하지 않는다. 담당자 집계의 이름을 누르면 해당 담당자 목록으로 이동한다.

## 홈 화면

- 최근 최대 100건으로 진행 중·완료 건수를 계산하던 방식을 없애고 전체 집계 API를 사용한다. 전체 평균 진행률과 위험도 건수도 표시한다.
- 최근 작업은 표시할 5건만 조회한다. 마감 목록은 별도의 서버 조건으로 진행 중이며 7일 후 날짜 이전인 작업을 마감일순으로 조회하므로 오래된 작업도 빠지지 않는다. 이미 마감이 지난 작업도 포함한다.
- 홈에는 마감 작업 5건을 표시하며 더 있으면 전체 건수와 전체 보기 링크를 제공한다. 링크 이동 후에도 진행 중·마감일·정렬 조건을 유지한다.
- 팀 Task와 개인 할 일의 데이터·조회 경로는 기존대로 분리한다. 이번 변경은 Task 집계를 위한 것이며 개인 할 일 저장 방식을 바꾸지 않는다.

## API

`GET /api/workspaces/{workspaceId}/tasks`의 기존 `page`, `size`, `mine`은 유지한다. 추가 조건은 다음과 같다.

| 조건 | 의미 |
|---|---|
| `assigneeId` | 양수인 담당자 ID. 해당 워크스페이스 작업만 조회 |
| `unassigned=true` | 담당자 미지정 |
| `status` | `IN_PROGRESS` 또는 `DONE` |
| `query` | 앞뒤 공백을 정리한 제목 부분 검색, 최대 200자 |
| `dueBefore` | ISO 날짜보다 이른 마감. 경계 날짜와 마감 미정은 제외 |
| `sort` | `RECENT` 기본값, 또는 `DUE_DATE` |

새 `GET /api/workspaces/{workspaceId}/tasks/progress`는 같은 조건(페이지·정렬 제외)에 해당하는 전체 집계를 반환한다.

```json
{
  "data": {
    "asOfDate": "2026-11-20",
    "overall": {
      "totalCount": 3, "inProgressCount": 2, "doneCount": 1, "progress": 44,
      "normalCount": 3, "warningCount": 0, "dangerCount": 0
    },
    "byAssignee": [{
      "assigneeId": 1,
      "summary": {
        "totalCount": 1, "inProgressCount": 1, "doneCount": 0, "progress": 33,
        "normalCount": 1, "warningCount": 0, "dangerCount": 0
      }
    }]
  }
}
```

`assigneeId=null`인 집계 항목이 미지정이다. 특정 담당자·내 담당·미지정을 동시에 상충하게 보내면 400이다. 다른 담당자 ID로 다른 워크스페이스의 작업을 읽을 수 없으며, 로그인·워크스페이스 멤버십 검사를 유지한다.

## 구현 범위

- C 파트의 TaskReadRepository/TaskReadService가 목록과 집계 조회를 맡는다. DB에서 필요한 Task 필드와 산출물 개수만 한 행으로 조회한다. 파일·본문·산출물 Entity 전체를 로딩하지 않으며 Task별 추가 쿼리를 만들지 않는다.
- 목록의 조건·개수·정렬·페이지는 DB에서 처리한다. 집계는 조건에 맞는 전체 Task의 간단한 projection으로 계산한다. 읽기 트랜잭션은 같은 요청 내에서 일관된 스냅샷을 사용한다.
- Task의 기존 진행률·위험도 계산을 공통 정적 메서드로 추출해 Entity와 projection이 같은 규칙을 쓴다.
- 기존 공유 TaskSummary와 TaskService 메서드의 시그니처는 유지한다. DB 필드·테이블·마이그레이션과 다른 파트의 Repository는 수정하지 않았다.

테스트용 PostgreSQL과 MockMvc로 121건 전체 집계, 100건 밖의 검색·마감, 필터 전 페이지 개수, Task 평균/산출물 가중치 구분, 위험도 경계, 담당자·미지정·작업 없는 팀원·이전 팀원, 빈 결과, 상태·제출 변경 반영, 안정적인 정렬, 인증·소속·입력 검증을 확인했다.

브라우저에서는 실제 Task/홈 컴포넌트와 확인용 API 응답으로 서로 다른 20개 시나리오를 확인했다. 페이지 이동 시 집계 유지, 필터 조합, 담당자별 목록 이동, 서버 검색, 빈 결과, 이전 응답 무시, 실패 안내·재시도, 홈의 전체 집계와 오래된 마감, 전체 보기 조건 유지, 좁은 영역 배치를 Task/홈 각각 1440px와 390px에서 반복 확인했다. 결과·화면은 작업 폴더 `output/progress-ui-20261120`에 있다.

실제 계정·사용자 DB E2E는 수행하지 않았다. 임시 확인용 서버·브라우저는 종료했고 개발 서버는 실행하지 않았다. 기존 500kB 초과 번들 경고는 남아 있다. 커밋·푸시·머지는 하지 않았다.

다음 우선순위는 Drive 동명 파일 덮어쓰기 선택과 기존 파일 크기 표시다.
