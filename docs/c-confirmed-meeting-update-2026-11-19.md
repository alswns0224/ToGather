# 확정 회의 수정과 Calendar 반영

2026-11-19. 설계 대조의 우선순위 5번(G04)을 보완했다. 기준은 SD-10-02(본문 71쪽), C-06-02(130쪽)다. 원본 저장소의 `feature/c-fix-task-rules`에서 앞선 Task·연동 보호 변경 위에 작업했다.

## 변경된 동작

- 확정된 회의도 제목, 확정 시작 시각, 소요 시간, 참여자, 진행 방식을 수정할 수 있다. 확정 상태는 유지하고 종료 시각은 시작 시각과 소요 시간으로 계산한다.
- 조율 중에는 기존 후보 기간 수정 방식을 유지한다. 확정 후에는 후보 기간 대신 확정 시각을 수정한다. 확정 시각을 원래 후보 기간 밖으로 옮길 수도 있다.
- 이미 등록된 일정이 있으면 같은 Calendar 일정 ID를 PATCH한다. 새 일정을 추가하는 방식으로 변경하지 않는다. Meet 생성 요청을 다시 보내지 않으며 기존 Meet 정보를 덮어쓰지 않는다. Calendar PATCH는 지정하지 않은 필드를 유지한다. [Google 공식 PATCH 문서](https://developers.google.com/workspace/calendar/api/v3/reference/events/patch)
- 확정 후 안건을 추가·변경·삭제해도 Calendar 설명의 안건 목록을 갱신한다.
- Calendar 반영에 실패해도 회의 변경과 확정 상태는 저장한다. `calendarSyncFailed=true`로 표시하고 상세 화면에서 재시도할 수 있다.
- 재시도는 DB에 저장된 최신 회의 정보와 참여자를 다시 보낸다. 기존 일정이 있으면 수정하고, 최초 등록 실패로 참조가 없으면 등록한다.
- 원본 일정이 삭제된 경우에는 자동 수정 중 새로 등록하지 않는다. 사용자가 삭제 시 재등록 안내를 확인하고 재시도할 때, 원본 삭제로 표시된 일정만 새로 등록한다. 이전 ContentRef는 삭제된 원본의 보관 기록으로 남긴다.
- 다른 사용자의 개인 Calendar 일정은 기존 접근 제한을 유지한다. 관리자는 ToGather 회의를 수정할 수 있지만 개인 일정 반영은 그 일정의 소유자가 재시도해야 한다. 접근 권한으로 인한 404를 원본 삭제로 간주해 복제하지 않는다.

## 캘린더 선택과 동시 변경

- 기존 팀 일정은 ContentRef에 저장된 캘린더 ID를 기준으로 그 대상을 선택한 연결을 찾는다. 기본 선택 순서가 바뀌어도 다른 캘린더에 반영하지 않는다.
- 원래 캘린더의 연결·선택이 없어졌으면 실패를 표시한다. 다른 캘린더나 요청자의 기본 캘린더로 대체하지 않는다. 원래 대상을 다시 연결한 뒤 재시도할 수 있다.
- `ContentRefService.getChannelId(contentRefId)`와 `IntegrationService.findTargetAccess(workspaceId, provider, targetId)`를 추가하고 공유 인터페이스 문서에 기록했다. 기존 메서드는 유지한다.
- 회의 수정·확정·취소·재시도·안건 변경은 같은 회의 행 잠금으로 직렬화한다. 가용 시간 저장과 추천 계산에도 같은 잠금을 적용해 기간·참여자 변경 중 옛 응답이 다시 저장되는 것을 막는다.
- 조율 중 후보 기간 변경은 기존처럼 응답·가용 시간·추천 후보를 초기화한다. 참여자를 수정하면 추천 후보도 다시 계산하도록 제거한다.

## 화면과 API

- 확정 회의에도 수정 버튼을 표시한다. 확정 시각 입력, Calendar 실패 안내, 재반영 버튼을 제공한다.
- 저장 중 입력과 중복 요청을 막고, 수정 중 취소·Calendar 재반영 요청도 비활성화한다.
- `PATCH /api/workspaces/{workspaceId}/meetings/{meetingId}`에 선택 필드 `startAt`을 추가했다. 기존 제목·시간·참여자 등의 필드는 유지한다. 응답 형식은 기존 MeetingDetailResponse다.
- `POST /api/workspaces/{workspaceId}/meetings/{meetingId}/calendar-retry`는 최초 등록뿐 아니라 실패한 기존 일정 갱신도 재시도한다. 정상 반영된 일정의 불필요한 재등록은 거절한다.
- 생성자·팀장·관리자의 수정 권한과 워크스페이스 멤버십 검사를 유지한다. 취소된 회의 수정, 잘못된 제목·소요 시간·시각·참여자는 거절한다.

DB 필드와 테이블을 변경하지 않아 이번 기능에는 새 마이그레이션이 없다. 다른 기능의 기존 변경과 별도 UI 실험본은 그대로 유지했다.

제외된 1개는 기존 `TogatherApplicationTests.contextLoads`이며 이번에 추가한 제외 항목은 없다. 프론트엔드의 기존 500kB 초과 번들 경고는 남아 있다.

테스트는 테스트용 PostgreSQL과 MockMvc, 외부 Calendar 클라이언트의 모의 응답을 사용한다.

- 확정 회의의 전체/부분 수정, 종료 시각 계산, 같은 일정·Meet 링크 유지, ContentRef 갱신
- Calendar 오류·재인증·연결 없음·사용 중 해제 실패 시 로컬 변경 보존과 최신 값 재시도
- 최초 등록 실패 복구, 삭제된 원본의 명시적 재등록, 다른 개인 일정 복제 방지
- 원래 대상과 다른 기본 캘린더 구분, 대상 해제 시 대체 금지, 실제 연결 선택 로직
- 확정 후 안건 변경 반영, 수정·취소 동시 요청의 직렬화
- 조율 중 기간 변경의 기존 초기화, 인증·권한·소속 검사와 잘못된 입력의 원자적 거절
- Calendar HTTP PATCH의 필드·수신자·주소 형식, 회의 정보 변경 시 conferenceData를 덮어쓰지 않는 요청

실제 Google 계정과 사용자 DB를 사용하거나 브라우저에서 직접 클릭하는 E2E를 수행하지 않았다. Calendar 화면에서 직접 수정하거나 Google Calendar에서 수정한 내용을 Meeting에 역방향 반영하는 기능은 이번 변경 범위에 포함하지 않는다.

커밋·푸시·머지와 개발 서버 실행은 하지 않았다. 다음 우선순위는 회의 안건별 자료·산출물 표시와 Slack의 연결 Task 표시다.
