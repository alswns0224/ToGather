# 기존 Task의 필수 산출물 항목 관리

2026-11-19. 설계 대조에서 정한 우선순위 4번(G01)을 보완했다. 기준은 SD-09-03(본문 65쪽), C-05-01/02(125~127쪽)다. 원본 저장소의 `feature/c-fix-task-rules`에 적용했고 별도 UI 실험본은 수정하지 않았다.

## 변경된 동작

- 생성된 Task의 상세 화면에서 산출물 이름과 선택 확장자를 입력해 항목을 추가할 수 있다. 항목 추가에는 Drive 연결이 필요하지 않다.
- 기존 항목은 제출 여부와 관계없이 삭제할 수 있다. 삭제 확인창에서 항목·제출 기록 삭제와 원본 Drive 파일 보존을 안내한다.
- 항목이 하나 이상이면 제출 비율로 진행률과 상태를 다시 계산한다. 모두 제출되면 완료, 하나라도 미제출이면 진행 중이다.
- 완료 Task에 미제출 항목을 추가하면 진행 중으로 돌아간다. 미제출 항목을 삭제해 남은 항목이 모두 제출된 경우에는 완료가 된다.
- 마지막 항목을 삭제하면 삭제 직전 상태를 유지한다. 항목이 없는 Task는 기존 규칙대로 상태를 수동 변경할 수 있고, 상태에 따라 진행률은 0% 또는 100%다.
- 제출된 항목 삭제는 해당 등록 정보만 제거한다. 원본 파일, ContentRef, 일반 관련 자료 연결, 같은 파일을 제출한 다른 Task는 유지한다.
- 화면에는 제출 개수/전체 개수, 항목 추가 폼, 항목별 삭제 버튼과 변경 결과를 표시한다. 실패 시 최신 상태를 다시 조회할 수 있다.

## API와 저장

| API | 성공 응답 | 동작 |
|---|---|---|
| `POST /api/workspaces/{workspaceId}/tasks/{taskId}/deliverables` | 201 + ApiResponse<TaskDeliverableSummary> | `{ "name": "발표 자료", "ext": "pdf" }`로 항목 추가 |
| `DELETE /api/workspaces/{workspaceId}/tasks/{taskId}/deliverables/{deliverableId}` | 204 | 항목과 해당 제출 메타데이터 삭제 |

이름은 공백만 허용하지 않고 최대 200자다. 확장자는 선택이며 최대 20자, 영문·숫자와 맨 앞 점 하나를 허용한다. 빈 값이나 null이면 확장자를 제한하지 않는다. 기존 `DeliverableInput` 검증을 재사용한다.

로그인, 워크스페이스 멤버십, Task 소속, 삭제 항목의 Task 소속을 검사한다. 일반 팀원도 관리할 수 있다. 기존 제출·제출 해제와 같은 Task 행 잠금을 사용해 변경을 직렬화한다.

Task 컬렉션의 기존 cascade/orphanRemoval로 항목을 저장·삭제한다. DB 필드·테이블·외래키 변경이 없어 이번 항목 관리에는 새 마이그레이션이 없다. 기존 제출·제출 해제 API와 공유 TaskSummary 형식은 유지한다.

## 검증 결과

| 검증 | 결과 |
|---|---|
| `backend/gradlew.bat build` | 성공 |
| 백엔드 전체 테스트 | 총 246개: 245개 통과, 기존 1개 제외, 실패·오류 0 |
| 신규 `DeliverableManagementTest` | 16개 모두 통과 |
| `frontend/npm run build` | 타입 검사·배포 빌드 성공 |
| `git diff --check` | 통과 |

신규 `DeliverableManagementTest`의 16개 사례는 테스트용 PostgreSQL과 MockMvc로 다음을 확인한다.

- Drive 미연결 상태의 추가, 이름 정리, 생성 ID 저장과 상세 응답 반영
- 제출 완료 후 추가, 미제출/제출 항목 삭제에 따른 상태·진행률 계산
- 마지막 항목 삭제 후 상태 유지와 수동 변경 복구
- 원본 콘텐츠·일반 자료 연결·다른 Task 제출 보존과 역방향 Task 조회
- 일반 팀원 허용, 미로그인·비멤버·다른 워크스페이스/Task 항목 차단
- 빈 이름, 잘못된 확장자, null 본문, 이름·확장자 길이 경계

외부 Drive API와 사용자 DB를 사용하지 않았다. 프론트엔드는 타입 검사·배포 빌드까지 검증했으며 브라우저에서 직접 클릭하는 E2E는 이번 검증에 포함하지 않았다. 기존 500kB 초과 번들 경고는 남아 있다.

제외된 1개는 기존 `TogatherApplicationTests.contextLoads`다. 이번 변경에서 추가한 제외 항목은 없다.

커밋·푸시·머지와 개발 서버 실행은 하지 않았다. 다음 우선순위는 확정 회의 수정 및 Calendar 반영이다.
